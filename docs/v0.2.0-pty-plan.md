## 1. Why v0.1.1 Is Not a Real Terminal

v0.1.1 is a well-built **command runner with a terminal-shaped UI**. The gap between
it and a real terminal emulator comes down to five fundamental missing pieces:

### 1.1 Hard-coded Command Allowlist

```rust
// commands/desktop/mod.rs  — v0.1.1
pub fn is_allowed_external(command: &str) -> bool {
    match command {
        "ls" | "dir" | "echo" | "whoami" | "cat" | "grep" | "curl" | "wget" => true,
        _ => false,  // git, cargo, python, ssh, vim … all rejected
    }
}
```

A real terminal never decides which commands are allowed. The **shell** does.
Blaze currently blocks `git`, `cargo`, `python`, `ssh`, `top`, `htop`, `npm`,
and every other program not on its list.

### 1.2 No PTY (Pseudo-Terminal)

Processes are spawned with `Stdio::piped()`:

```rust
// process.rs — v0.1.1
Command::new(&program)
    .stdout(Stdio::piped())   // child thinks it's writing to a file
    .stderr(Stdio::piped())
    .spawn();
```

When a child process is not attached to a PTY it:
- Disables its own color output (tools detect no TTY and strip ANSI)
- Disables interactive/raw-mode rendering (vim, htop, man, less)
- Buffers its output aggressively instead of line-buffering
- Cannot receive terminal signals (SIGWINCH for resize, etc.)

### 1.3 No ANSI / VT100 Rendering

Output arrives as raw bytes and is displayed verbatim inside `<div>` elements.
If a program outputs `\x1b[32mOK\x1b[0m` the terminal literally renders the
escape characters as visible text garbage instead of green "OK".

### 1.4 No Stdin to Running Processes

Once a command starts running, the user cannot interact with it.
There is no way to type into a `python` REPL, answer a `sudo` password prompt,
navigate `less`, or press `q` to quit `man`.

### 1.5 No Shell Subprocess

Blaze *is* the shell — it parses commands itself. A real terminal runs an
actual shell (`cmd.exe`, `powershell`, `bash`, `zsh`) as a child process and
simply acts as a display/input bridge. This means Blaze currently has no:
- PATH resolution for arbitrary programs
- Environment variable expansion
- Pipes (`cmd1 | cmd2`)
- Redirects (`cmd > file`)
- Shell scripting, aliases, functions

## 2. What v0.2.0 Must Achieve

| # | Requirement | Acceptance Criteria |
|---|---|---|
| R1 | Spawn a real shell inside a PTY | `cmd.exe` on Windows, `$SHELL` or `bash` on Unix |
| R2 | Any command runs | `git log`, `cargo build`, `python`, `ssh`, `vim`, `htop` all work |
| R3 | ANSI color + attributes rendered | `ls --color`, `git log --color`, bold/dim/italic/underline visible |
| R4 | Interactive programs work | `vim` opens and is fully usable; `python` REPL accepts input |
| R5 | stdin forwarded in real time | Keystrokes reach the running process immediately |
| R6 | Ctrl+C / Ctrl+D / Ctrl+Z work | Interrupt, EOF, suspend behave as expected |
| R7 | Terminal resize propagated | PTY and shell are notified when window is resized |
| R8 | Web demo unchanged | Web build still works; simulated commands still respond |
| R9 | All existing tests pass | No regressions in `web.rs`, `utils.rs` unit tests |
| R10 | Windows + Unix both work | ConPTY on Windows 10+; POSIX PTY on Linux/macOS |

## 4. New Dependencies

Add to `Cargo.toml` under the **non-wasm desktop** target block:

```toml
[target.'cfg(not(target_arch = "wasm32"))'.dependencies]
# existing
tokio  = { version = "1", features = ["process", "io-util", "sync", "rt"] }
image  = { version = "0.25", default-features = false, features = ["png"] }

# new in v0.2.0
portable-pty = "0.8"   # Cross-platform PTY: ConPTY on Windows, POSIX on Unix
vt100        = "0.15"  # VT100 / ANSI escape code parser + screen buffer
```

**Why `portable-pty`?**  
Written by the Wez Terminal author. Abstracts over Windows ConPTY
(`CreatePseudoConsole` API, Windows 10 1903+) and POSIX `openpty`. Gives a
uniform `PtyPair` with master/slave handles and a `Child` handle.

**Why `vt100`?**  
Pure Rust. Maintains a virtual screen grid (rows × cols) where each cell holds
a character plus full SGR attributes (fg color, bg color, bold, italic,
underline, dim, blink, reverse). Supports 256-color and truecolor.
Lighter than `alacritty_terminal` and sufficient for v0.2.0.

**Platform notes:**
- Windows: ConPTY requires Windows 10 build 1903 (May 2019 Update) or later.
  `portable-pty` will fail gracefully on older builds — surface a clear error
  message in the UI rather than panicking.
- `winres` and `ico` build-dependencies are unchanged.

## 5. New Architecture

### v0.1.1 (current)

```
User types
    │
    ▼
[Dioxus <input>]
    │  onkeydown: Enter
    ▼
[Blaze parses command string]   ← Blaze IS the shell
    │
    ├─ built-in? → handle internally
    └─ external? → allowlist check → spawn with Stdio::piped()
                                          │
                                    capture stdout/stderr as text
                                          │
                                    push Vec<TerminalLine>
                                          │
                                    render as <div> per line
```

### v0.2.0 (target)

```
User types
    │
    ▼
[Dioxus key capture div (tabindex=0)]
    │  onkeydown: any key
    ▼
[keys.rs — KeyboardEvent → &[u8]]
    │  e.g. Enter→\r, Ctrl+C→\x03, ArrowUp→\x1b[A
    ▼
[tokio mpsc Sender<Bytes>]  ──────────────────────────────────┐
                                                               │
                                                               ▼
                                                    [PTY write task]
                                                               │
                                                    writes bytes to PTY master
                                                               │
                                            ┌──────────────────┘
                                            │
                                     [PTY master fd]
                                            │   (ConPTY / POSIX pty)
                                            │
                                     [PTY slave fd]
                                            │
                                     [Shell process]   cmd.exe / bash / zsh
                                            │
                                     (shell runs any program the user types)
                                            │
                                     [PTY master fd] ← output bytes back
                                            │
                                            ▼
                                    [PTY read task]
                                            │
                                            ▼
                                    [vt100::Parser]
                                    feeds raw bytes, maintains screen grid
                                            │
                                            ▼
                                    [ScreenSnapshot] — Signal<ScreenSnapshot>
                                            │
                                            ▼
                                    [renderer.rs]
                                    screen grid → Vec of styled RSX spans
                                            │
                                            ▼
                                    [Dioxus re-render]
```

**Key insight:** Blaze v0.2.0 is no longer a shell. It is purely a
**display + input bridge** between the user and the OS shell. The shell
subprocess owns all command logic, history, completion, and environment.

#### 1.2 Create `src/terminal/screen.rs`

Define the types that the renderer and the PTY session will share:

```rust
/// A 24-bit RGB color.
#[derive(Clone, Debug, PartialEq)]
pub struct Rgb {
    pub r: u8,
    pub g: u8,
    pub b: u8,
}

/// The visual style of a single screen cell's text run.
#[derive(Clone, Debug, PartialEq)]
pub struct CellStyle {
    pub fg: Option<Rgb>,   // None = terminal default
    pub bg: Option<Rgb>,   // None = terminal default
    pub bold:      bool,
    pub italic:    bool,
    pub underline: bool,
    pub dim:       bool,
    pub blink:     bool,
    pub reverse:   bool,
}

/// A contiguous run of characters that share the same style.
#[derive(Clone, Debug, PartialEq)]
pub struct StyledRun {
    pub text:  String,
    pub style: CellStyle,
}

/// One rendered row in the terminal.
#[derive(Clone, Debug, PartialEq)]
pub struct ScreenRow {
    pub runs: Vec<StyledRun>,
}

/// An owned, diffable snapshot of the entire screen state.
/// Produced by the PTY read task; consumed by the Dioxus renderer.
#[derive(Clone, Debug, PartialEq)]
pub struct ScreenSnapshot {
    pub rows:       Vec<ScreenRow>,
    pub cursor_row: usize,   // 0-based
    pub cursor_col: usize,   // 0-based
    pub title:      String,  // from OSC 0/2 sequences
    pub cols:       u16,
    pub lines:      u16,
}
```

### Phase 2 — PTY Backend

**Goal:** Implement the PTY session module. No UI changes yet.

#### 2.1 Create `src/terminal/pty/mod.rs`

This module owns the entire backend lifetime:

```
PtySession {
    writer:    tokio::sync::mpsc::UnboundedSender<Vec<u8>>,
    resize_tx: tokio::sync::mpsc::UnboundedSender<PtySize>,
    title:     Signal<String>,
    screen:    Signal<ScreenSnapshot>,
}
```

**`PtySession::spawn(cols, rows, screen, title) -> Result<PtySession>`**

Steps inside `spawn`:

1. Create a `portable_pty::PtySystem` (native system implementation).
2. Open a `PtyPair` with initial size `PtySize { rows, cols, .. }`.
3. Resolve the shell binary:
   - Windows: prefer `powershell.exe`, fall back to `cmd.exe`.
   - Unix: read `$SHELL`, fall back to `bash`, then `sh`.
4. Build a `CommandBuilder` for the shell with no extra arguments
   (interactive login shell behavior is controlled by the shell's own config).
5. Spawn the child on the PTY slave.
6. Create two `tokio` tasks:

**Read task:**
```
loop {
    read bytes from PTY master into a buffer
    feed buffer into vt100::Parser
    snapshot vt100::Screen → ScreenSnapshot  (via render helper)
    write snapshot into Signal<ScreenSnapshot>
    check if child has exited → break if so
}
```

**Write task:**
```
loop {
    recv Vec<u8> from mpsc channel
    write bytes to PTY master
}
```

7. Create a **resize task** that receives `PtySize` messages and calls
   `pty_master.resize(size)` and `vt100_parser.set_size(rows, cols)`.

8. Return `PtySession { writer, resize_tx, screen, title }`.

**Important implementation notes:**

- The `vt100::Parser` is `!Send`, so it must live entirely within the read
  task. Do not try to share it across threads.
- PTY master I/O is blocking (even on `portable-pty`). Wrap the read and
  write loops in `tokio::task::spawn_blocking` or use a dedicated
  `std::thread::spawn`.
- The `ScreenSnapshot` conversion from `vt100::Screen`:
  - Iterate `screen.rows_formatted(0..rows)` — this gives `Cell` iterators.
  - Group adjacent cells with identical styles into `StyledRun` segments.
  - Convert `vt100::Color` to `Rgb`: handle `Default`, `Idx(n)` (256-color
    palette lookup), and `Rgb(r,g,b)` (truecolor).
  - Read `screen.title()` for the OSC window title.
  - Read `screen.cursor_position()` for the cursor coordinates.

### Phase 3 — Key Encoding

**Goal:** Map every Dioxus `KeyboardEvent` to the correct byte sequence.

#### 3.1 Create `src/terminal/pty/keys.rs`

Implement:

```rust
/// Convert a Dioxus KeyboardEvent into the byte sequence that should be
/// written to the PTY master.
/// Returns None for modifier-only keys (Shift, Alt, Ctrl alone).
pub fn key_event_to_bytes(event: &KeyboardEvent) -> Option<Vec<u8>>
```

The mapping table (partial — implement all):

| Key | Bytes |
|---|---|
| Printable char (no Ctrl) | UTF-8 bytes of the character |
| `Enter` | `\r` (0x0D) |
| `Backspace` | `\x7f` (DEL) |
| `Tab` | `\x09` |
| `Escape` | `\x1b` |
| `ArrowUp` | `\x1b[A` |
| `ArrowDown` | `\x1b[B` |
| `ArrowRight` | `\x1b[C` |
| `ArrowLeft` | `\x1b[D` |
| `Home` | `\x1b[H` |
| `End` | `\x1b[F` |
| `PageUp` | `\x1b[5~` |
| `PageDown` | `\x1b[6~` |
| `Delete` | `\x1b[3~` |
| `Insert` | `\x1b[2~` |
| `F1`–`F4` | `\x1bOP`–`\x1bOS` |
| `F5`–`F8` | `\x1b[15~`–`\x1b[19~` (skip 16) |
| `F9`–`F12` | `\x1b[20~`–`\x1b[24~` |
| `Ctrl + a`–`z` | `\x01`–`\x1a` (letter byte AND 0x1f) |
| `Ctrl + C` | `\x03` |
| `Ctrl + D` | `\x04` |
| `Ctrl + Z` | `\x1a` |
| `Ctrl + L` | `\x0c` (clear screen signal) |
| `Ctrl + U` | `\x15` (kill line) |
| `Ctrl + W` | `\x17` (kill word) |
| `Ctrl + R` | `\x12` (reverse history search) |

**Notes:**
- Check `event.modifiers()` for `Ctrl`, `Alt`, `Shift`.
- Alt + key → prepend `\x1b` to the key's normal bytes.
- Ctrl+C must NOT be blocked by the browser/webview — test early on Windows
  and Linux. In the Dioxus desktop webview, `prevent_default()` in
  `onkeydown` should be enough.
- Keys that have no terminal meaning (CapsLock, NumLock, PrintScreen) →
  return `None`.

### Phase 4 — Screen Renderer

**Goal:** Turn a `ScreenSnapshot` into Dioxus RSX.

#### 4.1 Create `src/terminal/pty/renderer.rs`

Implement:

```rust
/// Render a ScreenSnapshot as a Dioxus Element.
/// Each row becomes a <div class="pty-row">.
/// Each StyledRun becomes a <span> with inline CSS for color/attributes.
#[component]
pub fn PtyScreen(snapshot: ReadOnlySignal<ScreenSnapshot>) -> Element
```

**Rendering rules:**

- Each `ScreenRow` → `div { class: "pty-row", ... }`.
- Each `StyledRun` → `span { style: "...", "{run.text}" }`.
- Build the `style` attribute string:
  - `color: rgb(r,g,b)` if `fg` is `Some`.
  - `background-color: rgb(r,g,b)` if `bg` is `Some`.
  - `font-weight: bold` if `bold`.
  - `font-style: italic` if `italic`.
  - `text-decoration: underline` if `underline`.
  - `opacity: 0.5` if `dim`.
- Cursor cell: render a `span` with an additional `pty-cursor` CSS class.
  The CSS will make it a blinking block or bar.
- Empty rows: render a `div { class: "pty-row", "\u{00A0}" }` (non-breaking
  space to preserve row height).
- Wrap everything in `div { id: "pty-screen", class: "pty-screen", ... }`.

**Performance note:** Dioxus diffs the virtual DOM — rendering 80×24 = 1,920
spans on every byte of output would be expensive. Mitigate by:
1. Only re-render when the `ScreenSnapshot` actually changes (Dioxus signals
   already gate this on `PartialEq`).
2. Keep `PartialEq` on `ScreenSnapshot` cheap — it is derived, so it compares
   field by field. Consider a `revision: u64` counter instead of deep-comparing
   all rows if performance is an issue.

### Phase 5 — New Desktop Component

**Goal:** Replace `DesktopTerminal` with `PtyTerminal` that wires together
the PTY backend, key encoder, and screen renderer.

#### 5.1 Replace `DesktopTerminal` in `src/terminal/components.rs`

```rust
#[cfg(all(feature = "desktop", not(target_arch = "wasm32")))]
#[component]
pub fn PtyTerminal() -> Element {
    // 1. Create signals for screen and title.
    let mut screen   = use_signal(ScreenSnapshot::default);
    let mut title    = use_signal(|| "⚡ Blaze Terminal".to_string());
    let mut pty      = use_signal(|| Option::<PtySession>::None);
    let mut pty_cols = use_signal(|| 80u16);
    let mut pty_rows = use_signal(|| 24u16);

    // 2. On first mount, spawn the PTY session.
    use_effect(move || {
        if pty().is_none() {
            match PtySession::spawn(pty_cols(), pty_rows(), screen, title) {
                Ok(session) => pty.set(Some(session)),
                Err(e) => { /* push error into a fallback message signal */ }
            }
        }
    });

    // 3. Key handler: encode and send to PTY.
    let handle_key = move |e: KeyboardEvent| {
        e.prevent_default();
        if let Some(session) = pty().as_ref() {
            if let Some(bytes) = key_event_to_bytes(&e) {
                let _ = session.writer.send(bytes);
            }
        }
    };

    // 4. Auto-scroll: re-run on every screen change.
    use_effect(move || {
        let _ = screen();
        document::eval(
            r#"setTimeout(()=>{
                let s=document.getElementById('pty-screen');
                if(s)s.scrollTop=s.scrollHeight;
            },10)"#,
        );
    });

    // 5. Render.
    rsx! {
        div {
            class: "terminal-container terminal-fullscreen",
            tabindex: "0",
            onkeydown: handle_key,

            div { class: "terminal-header",
                span { class: "terminal-title", "{title}" }
                div { class: "terminal-controls",
                    button { class: "win-btn win-btn-minimize",
                        onclick: move |_| dioxus::desktop::window().set_minimized(true),
                        "−"
                    }
                    button { class: "win-btn win-btn-maximize",
                        onclick: move |_| dioxus::desktop::window().toggle_maximized(),
                        "□"
                    }
                    button { class: "win-btn win-btn-close",
                        onclick: move |_| dioxus::desktop::window().close(),
                        "✕"
                    }
                }
            }

            PtyScreen { snapshot: screen.into() }
        }
    }
}
```

## 8. Key Design Decisions

### 8.1 Shell Choice

| Platform | Primary | Fallback |
|---|---|---|
| Windows | `powershell.exe` | `cmd.exe` |
| Linux | `$SHELL` env var | `bash` → `sh` |
| macOS | `$SHELL` env var | `zsh` → `bash` → `sh` |

Rationale: PowerShell is the modern Windows shell with good ANSI support.
On Unix, respect the user's configured shell.

### 8.2 No Custom Shell Parsing

v0.2.0 removes ALL of Blaze's custom command parsing (`split_args`, the
match dispatch, the allowlist). The shell subprocess handles 100% of command
parsing, PATH lookup, piping, and redirection. Blaze sends raw keystrokes and
displays raw output. This is the correct separation of concerns.

### 8.3 VT100 Screen Buffer vs. Line Buffer

v0.1.1 appended output line-by-line (`Vec<TerminalLine>`). v0.2.0 maintains
a fixed-size screen grid via `vt100::Parser`. This correctly handles:
- Cursor movement (vim, htop moving the cursor around)
- In-place updates (progress bars using `\r`)
- Screen clearing (`\x1b[2J`)
- Alternate screen buffer (used by vim, less, man)

### 8.4 Input Capture Strategy

Replace the `<input type="text">` with a `<div tabindex="0">` on the
outermost terminal container and attach `onkeydown`. This captures all
keys including Tab, Escape, F-keys, and Ctrl combos that an `<input>` would
either block or handle natively. Call `e.prevent_default()` on every
captured keystroke to prevent the webview from acting on them.

### 8.5 Scrollback

`vt100` does not maintain a scrollback buffer — only the current screen.
For v0.2.0, scrollback is left to the shell's `less`/`more` pager and the
terminal's alternate screen buffer. A native Blaze scrollback buffer
(storing screen history) is a v0.3.0 concern.

### 8.6 Web Demo Is Untouched

The web feature (`dx serve --platform web`) compiles to WASM. `portable-pty`
and `vt100` are behind `#[cfg(not(target_arch = "wasm32"))]` guards and are
never compiled for the web target. The web demo continues to use the
simulated `run_web_command` path unchanged.

## 9. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| ConPTY not available on old Windows builds | Low | High | Detect at runtime; show a clear "requires Windows 10 1903+" error in the UI instead of crashing |
| `vt100` crate doesn't handle all escape sequences | Medium | Medium | Most common sequences are covered; edge cases can be filed as issues and patched; the shell still works, output just may not render perfectly |
| Dioxus `onkeydown` doesn't capture all keys in the webview | Medium | High | Test early (Phase 3); fall back to a JS `addEventListener('keydown')` injected via `document::eval` if Dioxus events miss keys |
| PTY read blocking the Dioxus event loop | Low | High | Always run PTY I/O on a separate `std::thread` or `spawn_blocking`; never block the Dioxus async executor |
| Resize calculation is wrong (font metrics) | Medium | Low | Start with a hardcoded 80×24; add dynamic resize after the core works |
| `vt100::Parser` `!Send` causes thread issues | Medium | High | Keep the parser exclusively inside the read task/thread; communicate via `Signal<ScreenSnapshot>` only |
| Web build broken by new imports | Low | High | All new modules are behind `#[cfg(not(target_arch = "wasm32"))]`; run `dx build --platform web` at the end of every phase |
| `portable-pty` crate compilation issues on some targets | Low | Medium | Pin to a tested version; `portable-pty = "0.8"` is well-maintained |
